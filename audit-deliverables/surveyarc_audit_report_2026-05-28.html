Executive Opinion

SurveyArc is not a small demo application. The repository contains a broad, multi-service product foundation with survey authoring as the central business value, plus supporting modules for organization management, project management, contacts, campaigns, quota, translations, RBAC, ticketing, SLA operations, Salesforce, payments/pricing, marketplace, integrations, webhooks, mail relay, and encryption-related services.

The survey product is the main asset being valued in this report. It already includes a visual survey builder, a large question-type library, blocks and ordering, survey runtime rendering, response handling, quota/rule infrastructure, translation support, templates, theme support, campaign integration points, and an XML survey programming mode. These features represent substantial development effort and give an acquiring internal team a meaningful head start compared with starting from zero.

Recommended Price Position

Recommended opening pitch for complete code transfer: INR 18,00,000 to INR 22,00,000

Practical negotiation target: INR 14,00,000 to INR 17,00,000

Minimum sensible floor for the full repository with KT: INR 11,00,000 to INR 12,50,000

The above assumes an as-is code transfer, documentation bundle, and reasonable knowledge transfer support. It is not priced as a fully supported commercial SaaS.

This assessment uses an internal-use acquisition lens. Since the buyer intends to use and extend the tool internally, the valuation should not be judged only by public SaaS readiness. Internal-use buyers can accept unfinished polish if the architecture, data model, and business modules save significant development time.

3. Survey System Deep Dive

The survey system is the main value driver. It combines a visual builder, backend schema, frontend state management, question configuration forms, survey runtime, response capture, translation support, quota/rule foundations, template creation, and campaign-related delivery surfaces. For an internal buyer, this survey foundation is the strongest reason to acquire the repository instead of building from scratch.

3.1 Survey Data Model and Backend APIs

The backend survey model stores the survey as an organization/project-owned object with survey identity, name, slug, version, status, settings, question order, theme association, blocks, and block order. This is important because it supports both simple linear surveys and more complex block-based survey programming.

Survey Capability Evidence in Codebase Assessment

Survey status Survey schema/model carries status fields; frontend displays draft/live states. Useful foundation, but status synchronization between inner builder and outside listing needs final consistency checks.
Question order Survey payload supports question_order and frontend maps questionOrder to backend shape. Necessary for stable survey rendering and survey programming.

Responses count and response listing Survey routes expose response count and response listing per survey. Basic reporting and operational visibility are present.

Locales Survey route exposes survey locales and question translation APIs exist. Translation architecture is present and valuable for multilingual internal survey work.

3.2 Question Data Model

Questions are modeled with both internal identity and human-facing labels. The backend stores question_id as the primary key and serial_label as the reference label used for programming, logic, exports, and human readable references such as Q1, Q2, Q3, etc. This is the correct direction because internal IDs should not be exposed as the main survey-programming reference.

Question Field Purpose Value
question_id System-level unique identifier, primary key. Prevents internal collisions and allows stable database references.
serial_label Human-facing survey programming label such as Q1, Q2, S1, etc. Better UX for logic, exports, XML mode, and analyst workflows.
type Controls renderer/config editor behavior. Supports broad question library and screen types.
label The actual respondent-facing question text. Core survey content field.
description Helper text or subtext. Supports richer survey authoring.
config Question-type-specific JSON configuration. Enables flexible advanced question types without changing the base table repeatedly.
logic Per-question logic and branching actions. Important for future survey programming maturity.
translations Localized labels/descriptions/configs. Important for multilingual internal deployments.
